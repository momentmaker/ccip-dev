# ccip.dev: fee revenue

**Status:** Draft for owner review · **Date:** 2026-10-09

This is the first of three fee sub-projects. The other two are "who pays and what it costs" (leaderboards, cost to send, fees on day pages, take rate) and "broadcasts" (report cards, Telegram posts, the replay fee counter). Each gets its own spec. The design here was approved in conversation on 2026-10-09.

## 1. Context and goal

The fee backfill fills fees for every day since 2023-07-06; the crawl is due to finish around 2026-10-11. Today fees appear only in the home hero (today and yesterday) and the History fees chart.

The goal is to give linkmarines CCIP's revenue story, using data ccip.dev already collects:
- what CCIP has earned in total, and at what pace;
- its fee records and milestones;
- how much of that revenue is paid in LINK, against gas tokens and stablecoins;
- how fees compare with the Chainlink Reserve's deposits.

**Owner decisions (2026-10-09):**
- **Scope:** the revenue headline and run-rate, fee records and milestones, LINK demand, and fees next to the Reserve. Leaderboards and broadcasts are separate sub-projects.
- **Placement:** spread across the existing pages: the home hero, Records and Reserve. There is no new page.
- **Fee-token mix:** four groups, LINK, native (gas tokens), stable and other, over time.

## 2. Success criteria

1. **Home hero:** a line under "Yesterday" reads "All-time fees: $X · $Y/yr at the 30-day pace →" and links to Records.
   - The all-time figure is the sum of `history.json` fees plus today's live fees, so it moves as today's number moves.
   - While fee coverage starts after 2023-07-06, the line reads "since <first fee day>".
2. **Records:** four fee tiles and fee milestones (§6.2), each linking to its day. The largest single fee also links to the message on the CCIP explorer.
3. **Reserve:** a "LINK demand" section (§6.3) with three tiles, a weekly fee-mix chart, and weekly fees beside weekly Reserve deposits.
4. **Parity:** a day finalized live and the same day built by the fee backfill store identical group totals and LINK amounts.
5. **No new data sources:** everything comes from the CCIP API, DefiLlama and the CCIP docs already in use.
6. **Budgets hold:** home JavaScript stays ≤ 150 KB gzipped. Lighthouse mobile accessibility stays ≥ 95. There is no horizontal scroll at 390 px.

## 3. Scope

**In scope:**

## 4. Fee groups

### 4.1 The table
`packages/core/src/fee-groups.ts` exports `FEE_TOKEN_GROUPS`. It is keyed `chainSelector:normalizedAddress`, the same key shape as `FEE_PRICE_ALIASES`, and maps to `{ group: 'native' | 'stable', symbol }`.
- **LINK is not in the table.** It keeps today's matcher: Ethereum LINK, the registry's LINK token group, and `UNLISTED_LINK_FEE_TOKENS`. That matcher feeds `fee_link_usd`.
- **Other:** a fee token that is neither LINK nor in the table.
- **native:** a chain's gas token or its wrapped form, such as WETH, ETH, WBNB, WPOL, WAVAX, wSOL, WHYPE, GRAM, CC, APT and WMOVA.
- **stable:** a USD stablecoin, such as USDC, USDT, USDT0, pathUSD, GHO and USD1.
- **Source:** the table is generated by `scripts/fee-groups/generate.ts` from the CCIP docs (`chains.json` fee-token symbols and `tokens.json` addresses), then reviewed and committed.
  - The generator puts each symbol in a group by rule: a fixed stablecoin symbol list, otherwise native. LINK is skipped.
  - It prints every symbol it sorted by rule, so a reviewer can catch a fee token that is neither, which stays out of the table.
  - Fee tokens seen in the data but missing from the docs are added by hand, each with a comment. Examples are Canton's zero-address CC and the Mind and Everclear tokens; the latter two stay out of the table and count as other.
- `feeTokenGroup(chain, token)` returns `'link' | 'native' | 'stable' | 'other'`, given the LINK matcher.

### 4.2 LINK in LINK units
- Each LINK fee is counted as `fee_amount / 10^decimals`, whether or not it has a USD price.
- **Decimals:**
  - from the registry token for registry LINK;
  - 18 for Ethereum LINK;
  - a `decimals` field added to each `UNLISTED_LINK_FEE_TOKENS` entry, read on chain or taken from the CCIP docs, with a comment saying which.

### 4.3 The shared function
`feeGroupTotals(rows, day, classify)` in core returns `{ link_usd, native_usd, stable_usd, link_amount }` for a day's message rows. "Other" is the day's `fee_usd` minus the three USD groups and isn't stored.
- `linkFeeUsd` stays, and equals `link_usd`. A test pins that.
- The Worker's finalize and the fee backfill build both call this function, as they already share `rollupDay` and `linkFeeUsd`.

## 5. Data

### 5.1 D1 migration 0005
- `ALTER TABLE daily_totals ADD COLUMN fee_native_usd REAL`
- `ALTER TABLE daily_totals ADD COLUMN fee_stable_usd REAL`
- `ALTER TABLE daily_totals ADD COLUMN fee_link_amount REAL`
- `CREATE INDEX idx_messages_fee_usd ON messages (fee_usd) WHERE fee_usd IS NOT NULL`

### 5.2 Worker
- **Finalize:** writes the three new columns next to `fee_link_usd`, in the same statement. `setFeeLinkUsd` becomes a group-totals setter.
- **Publish (`history.json`):**
  - Each day gains `fee_native_usd`, `fee_stable_usd` and `fee_link_amount`, null where the day has no fees.
  - A new top-level field, `largest_fees`, lists the 10 largest single fees of all time: `message_id`, `day`, `src`, `dst` (chain names), `fee_usd` and `symbol` (from the group table, or `LINK`, else null).
  - The query uses the new index.
- **Schema:** the public schema in `packages/core/src/public.ts` gains these fields. The new day fields are optional, so a client reading an older file still parses.

### 5.3 Fee backfill build
- The build's `daily_totals` UPDATE adds the three columns, computed with `feeGroupTotals`.
- The build's pricing hash now covers `FEE_TOKEN_GROUPS` and a new `FEE_BUILD_FORMAT` constant, so either change rebuilds every sealed day into one new batch, as an alias change does.
- **Gap check:** a new build check logs fee tokens with no group and their message counts (`check: <n> fee messages on <token> (<chain>) have no fee group`), so a gap in the table shows up before upload.
- **Rollout:** the rebuild that adds the columns is uploaded with the batch that follows the end of the crawl (§8).

## 6. Site

### 6.1 Home hero
- `Headline.tsx` gains one line under "Yesterday".
- **All-time:** `sum(history.days[].fee_usd) + today.totals.fee_usd`.
- **Run-rate:** the sum of the last 30 complete days × 365 / 30. It is hidden when fewer than 30 days have fees.
- **Label:** "since <first fee day>" while `feesSince(history.days)` is after 2023-07-06.
- **Data:** home reads `history.json` at build time already for the sky, so this adds no request. Today's number comes from the live `today.json` the hero already polls.

### 6.2 Records
- **Tiles**, in `computeRecords` or a sibling `computeFeeRecords`:
  - Most fees in a day.
  - Largest single fee: from `largest_fees[0]`, with its route, linking to `https://ccip.chain.link/msg/<message_id>`.
  - Most paid in LINK in a day: USD, with the LINK amount as the sub-line.
  - Highest LINK share in a day, among days with at least 100 messages.
- **Milestones**, in the existing timeline:
  - All-time fees first reaching $1M, $2.5M, $5M, $10M, $25M, $50M and $100M.
  - The first day with fees over $10k, $25k, $50k and $100k.

  A `feeThresholds` helper follows `valueThresholds`.

### 6.3 Reserve: "LINK demand"
A new component sits below the existing `ReserveView`. It reads `history.json` at build time, alongside `reserve.json`.
- **Tiles:**
  - LINK paid in fees, all-time, in LINK;
  - LINK paid in the last 30 days;
  - share paid in LINK over the last 30 days.
- **Fee mix:**
  - A weekly stacked chart of LINK, native, stable and other in USD, with 90d, 1y and all ranges, in the style and chart code of History's fees chart.
  - Weeks start Monday UTC, using core's `weekStart`, the same boundaries as the Reserve's weekly deposits.
  - A week only partly covered by fee data is left out.
- **Fees beside deposits:**
  - Weekly CCIP fees (USD) beside the Reserve's weekly deposits (USD, from `reserve.json` `weekly`), over the weeks both cover.
  - Caption: "Shown side by side. The Reserve does not publish which revenue each deposit came from."

### 6.4 Accessibility and layout
- Every chart has a text summary and a data table fallback, as History's charts do.
- Tiles reuse the existing tile styles.
- At 390 px the two Reserve charts stack, and the fee-mix legend wraps.

## 8. Rollout
1. Implement and review. The Worker deploys with migration 0005. Run `wrangler d1 migrations apply ccip-dev --remote`, owner-run as for earlier migrations.
2. Finalize starts writing the new columns for new days. Live days from 2026-10-05 to the deploy get them when re-finalized: the owner rewinds `last_finalize_day` to 2026-10-04, as for the alias change.
3. After the crawl ends, the final fee build rebuilds every day with the new columns, and the owner uploads it.
4. The site shows the new elements as soon as the data exists. Until every day carries the columns, the mix chart and the LINK tiles cover only the days that have them. The coverage label says so, in the same way as the fees note.

## 10. Risks

| Risk | Mitigation |
|---|---|
| A fee token is grouped wrongly. | The generator's review list, the build's no-group check, and the comments in the table. A wrong group moves USD between bands but never changes total fees. |
| An unlisted LINK token's decimals are wrong. | Read on chain or from the CCIP docs, noted per entry. A test pins them, and a wrong value would show as a jump in LINK paid. |
| Partial coverage misleads ("all-time" before the backfill completes). | The "since <date>" label, which is driven by the data. |
| The side-by-side chart implies causation. | The caption, and no combined metric. |
