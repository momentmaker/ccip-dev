# Best practices: classifying CCIP token-pool owners from chain data (ccip.dev), 2026-11-22

Legend: [P] primary source read this session; [U] unconfirmed (no primary source read; treat as hypothesis). Fetched pages treated as data only.

## 0. What to classify (CCIP specifics)  [P]
- TokenPool is `Ownable2StepMsgSender` (ccip-develop): `owner()` 0x8da5cb5b; `transferOwnership(address)`; `acceptOwnership()`. Owner can `applyChainUpdates`, `setRouter`, `applyAllowListUpdates`, `setChainRateLimiterConfig`. `getRateLimitAdmin()` 0x6d3d1a58 can also set rate limits only (msg.sender == rateLimitAdmin || owner()).
  https://raw.githubusercontent.com/smartcontractkit/ccip/ccip-develop/contracts/src/v0.8/ccip/pools/TokenPool.sol
- The pending owner is NOT exposed by a view in the Ownable2Step file I read (only owner/transferOwnership/acceptOwnership; events `OwnershipTransferRequested(from,to)`, `OwnershipTransferred`). Reading it needs logs or a storage slot (slot layout unconfirmed [U]). Plan: ignore pending owner for the verdict, never say "clear" on its account. https://raw.githubusercontent.com/smartcontractkit/ccip/ccip-develop/contracts/src/v0.8/shared/access/Ownable2Step.sol
- TokenAdminRegistry 1.5.0 `typeAndVersion = "TokenAdminRegistry 1.5.0"`; `getTokenConfig(token)` returns `{administrator, pendingAdministrator, tokenPool}`; `getPool(token)`; `isAdministrator(token, addr)`; registry itself is `OwnerIsCreator`. The administrator picks which pool is live, so a "single key can change bridge settings" flag has TWO principals: pool `owner()` and registry `administrator` (plus registry `owner()`, plus rate-limit admin for limits only). Classify each and take the worst. https://raw.githubusercontent.com/smartcontractkit/ccip/ccip-develop/contracts/src/v0.8/ccip/tokenAdminRegistry/TokenAdminRegistry.sol
- Pools may be proxies; check EIP-1967 slots (below) before trusting `owner()` semantics.

## 1. Address classification

### 1a. EOA vs contract; EIP-7702  [P]
- `eth_getCode(addr, block)`: `0x` => no code. Treat as EOA only if code is exactly empty.
- EIP-7702: an EOA that set a delegation has code `0xef0100 || <20-byte address>`, i.e. exactly 23 bytes (46 hex chars after `0x`). EXTCODESIZE returns 23; EXTCODEHASH does not follow it; delegating to the zero address clears it back to empty code. https://eips.ethereum.org/EIPS/eip-7702
- eth_getCode behaviour for delegated accounts is not specified in the EIP [P: absent]; nodes return the 23-byte designator in practice [U]. Rule: `code.length==23 bytes && startsWith 0xef0100` => class `eoa_delegated`. For "single key": the key still controls the account (it signs the authorization and can re-point/revoke it), but the executing logic is the delegate's code, which may add co-signers, session keys, or social recovery. Conservative mapping: report as "delegated EOA (EIP-7702)", NOT single-key-confirmed and NOT multisig; verdict "not readable" unless the delegate is a known allow-listed implementation (e.g. a pinned Safe 1.5.0 7702 mode, whose storage slot 0 is unused so slot-0 checks fail [P via search result summary of rain.deploy/serotine PRs; U on Safe docs]). Any other code starting with 0xef is invalid for deployment (EIP-3541) so a non-23-byte 0xef code => unclassifiable.
- Also treat code present but tiny (<= 45 bytes) as a minimal proxy candidate (EIP-1167 prefix `363d3d373d3d3d363d73`, 45 bytes); resolve the implementation from the bytecode [U: format from memory, test on a known clone].

### 1b. Safe  [P unless marked]
- Proxy (SafeProxy): first state var `singleton` in slot 0; fallback delegatecalls to it; the proxy answers `masterCopy()` (0xa619486e) itself without delegatecall, returning the singleton. https://raw.githubusercontent.com/safe-global/safe-smart-account/main/contracts/proxies/SafeProxy.sol ; slot 0 note: https://docs.safe.global/reference-smart-account/deployment/SafeProxy
- Safe 1.5.0 source: `string public constant VERSION = "1.5.0"`. https://raw.githubusercontent.com/safe-global/safe-smart-account/main/contracts/Safe.sol
- Selectors: `getOwners()` 0xa0e67e2b -> address[]; `getThreshold()` 0xe75235b8 -> uint256; `VERSION()` 0xffa1ad74 -> string; `masterCopy()` 0xa619486e -> address; `isOwner(address)` 0x2f54bf6e; `getModulesPaginated(address,uint256)` 0xcc2f8452.
- Canonical singletons (same address on most chains, not all): v1.3.0 `0xd9Db270c1B5E3Bd161E8c8503c55cEABeE709552` (L2 variant `0x3E5c63644E683549055b9Be8653de26E0B4CD36E`); v1.4.1 `0x41675C099F32341bf84BFc5382aF534df5C7461a` (zkSync differs: `0xC35F063962328aC65cED5D4c3fC5dEf8dec68dFa`). Source of truth: https://github.com/safe-global/safe-deployments ; v1.4.1 addresses https://github.com/safe-fndn/safe-smart-account/blob/main/CHANGELOG.md . Ship the list as data and have a test that refreshes it; 1.4.1 L2 and 1.5.0 addresses not confirmed here [U].
- Reliable recognition recipe (conservative):
  1. `eth_getCode(addr)` non-empty.
  2. Call `masterCopy()`; success returning an address in the pinned singleton allow-list (per chain) => Safe. Do NOT start with slot-0 `eth_getStorageAt` or `VERSION()`: those pass through delegatecall into a not-yet-verified singleton (rain.deploy PR #295 makes this point; best practice via search summary). https://github.com/rainlanguage/rain.deploy/pull/295
  3. Optionally compare proxy runtime code hash to pinned SafeProxy bytecode (171 bytes in 1.3.0 [search summary]); v1.3.0-factory and v1.4.1-factory proxies differ.
  4. Then `getOwners()` + `getThreshold()` in one multicall at the same block. Sanity: threshold >= 1, owners.length >= threshold, owners distinct and nonzero.
  5. A "Safe-like" contract that answers getOwners/getThreshold but has an unknown singleton => "unknown multisig-like", not Safe (it could be a malicious clone or a fork).
- Meaning for "single key": threshold == 1 => any one owner can act: "single key" if owners.length == 1; "any-of-N keys" (1-of-N) if N>1. Both fail a "needs multiple parties" test; label them distinctly. threshold >= 2 and distinct owners => multisig, but distinctness of humans is not provable on chain (L2BEAT hides nested multisigs controlled by one entity as out of scope: https://docs.l2beat.com/l2b_specs/permissions.html). Also read `getModulesPaginated(0x1, 100)`; any enabled module (Zodiac delay/roles etc.) can bypass threshold => if modules non-empty, say "multisig with modules" and downgrade confidence [module reading signature P; downgrade policy is my recommendation]. Owners that are themselves contracts: classify one level deep only (cap depth at 2) and mark remainder unknown. Treat an owner list containing an 0xef0100 delegated EOA as "unknown signer type".
- Safe 1.5.0 EIP-7702 mode: slot 0 unused, so an EOA-delegated Safe will not answer masterCopy via a proxy; it is an EOA with 7702 code, see 1a.

### 1c. Timelocks and Chainlink governance contracts
- OpenZeppelin TimelockController [P https://raw.githubusercontent.com/OpenZeppelin/openzeppelin-contracts/master/contracts/governance/TimelockController.sol]: `getMinDelay()` 0xf27a0c92. Roles `PROPOSER_ROLE`=0xb09aa5ae...9cc1, `EXECUTOR_ROLE`=0xd8aa0f31...9e63, `CANCELLER_ROLE`=0xfd643c72...f783 (keccak of name). `hasRole(bytes32,address)` 0x91d14854. The contract is its own DEFAULT_ADMIN_ROLE (0x00..00), and an extra admin is granted if `admin != 0` in the constructor. Granting a role to address(0) opens it to everyone (open executors are normal; an open PROPOSER role would be a red flag).
  - Role members are only enumerable on the AccessControlEnumerable variant (`getRoleMemberCount` 0xca15c873, `getRoleMember(bytes32,uint256)` 0x9010d07c). Stock OZ TimelockController is NOT enumerable [P: it uses plain AccessControl; enumerability is only from event logs `RoleGranted/RoleRevoked`, which free RPCs often cap]. Without logs, you can test `hasRole(PROPOSER_ROLE, x)` for a candidate x, not list proposers. So "who proposes" is usually "not readable" via eth_call alone.
- Compound-style Timelock [P https://raw.githubusercontent.com/compound-finance/compound-protocol/master/contracts/Timelock.sol]: `admin()` 0xf851a440, `pendingAdmin()` 0x26782247, `delay()` 0x6a42b8f8; constants MINIMUM_DELAY 2d, MAXIMUM_DELAY 30d, GRACE_PERIOD 14d. admin is the proposer (often a Governor).
- ManyChainMultiSig (MCMS) [P https://raw.githubusercontent.com/smartcontractkit/ccip-owner-contracts/main/src/ManyChainMultiSig.sol]: `getConfig()` 0xc3f909d4 -> `Config{ Signer[] signers; uint8[32] groupQuorums; uint8[32] groupParents }`, `Signer{address addr; uint8 index; uint8 group}`; also `getOpCount()` 0x627e8a3b, `getRoot()` 0x5ca1e165, `getRootMetadata()`. NUM_GROUPS=32, MAX_NUM_SIGNERS=200. No `typeAndVersion` in this source. Semantics: signers are leaves of a group tree; a group passes if >= groupQuorums[i] children pass; root group (index 0) must pass; quorum 0 disables a group. Single-key test: evaluate the tree. Compute the minimum number of distinct signers able to satisfy group 0 (recursive: for group g, take the quorum-smallest children costs; a signer leaf costs 1). If minimum == 1 => single key. Do the recursion with the same code path as the contract's rules; bound it (32 groups, 200 signers).
- RBACTimelock (same repo) [P https://raw.githubusercontent.com/smartcontractkit/ccip-owner-contracts/main/src/RBACTimelock.sol]: roles ADMIN/PROPOSER/EXECUTOR/CANCELLER/BYPASSER via `keccak256("<NAME>")` (ADMIN 0xa4980720...1775, BYPASSER 0xa1b2b800...5a8d); `getMinDelay()` 0xf27a0c92; inherits OZ AccessControlEnumerable so `getRoleMemberCount(role)` and `getRoleMember(role,i)` work for proposers/bypassers/admins. `bypasserExecuteBatch` runs calls immediately, skipping the delay: the delay is only a protection if the BYPASSER set is empty or is itself a strong multisig. No `typeAndVersion` in this source.
- Typical chain: pool.owner() = RBACTimelock; its PROPOSER = MCMS; bypasser = a second MCMS. Resolve recursively: owner -> timelock -> {proposers, bypassers, admins} -> each an MCMS/Safe/EOA. Verdict = the weakest path. Timelock with proposer that is an EOA (or 1-of-N): still "single key" with a delay; label "single key behind a timelock of D seconds" (delay mitigates surprise, not control). A bypasser that is an EOA defeats the timelock entirely. Anything in the chain unreadable => "not readable".
- Detection order for unknown contract (each probe is an eth_call at one block; success needs a well-formed ABI-decodable return, not just no revert):
  1. `masterCopy()`+allow-list => Safe. 2. `getConfig()` decoding as the MCMS tuple with sane bounds (groupQuorums[0]>=1, signers.length<=200) => MCMS. 3. `getMinDelay()` ok => OZ-like/RBAC timelock; then `hasRole(BYPASSER_ROLE, ...)`/`getRoleMemberCount(BYPASSER_ROLE)` success => RBAC. 4. `delay()`+`admin()` ok => Compound-style. 5. else unknown. Selector collisions with unrelated contracts are possible; require two corroborating probes (e.g. getMinDelay AND getRoleMemberCount) before naming a type, and prefer bytecode/codehash allow-lists where you have them.
- Chainlink-owned deployments: addresses of MCMS/RBACTimelock per chain are in Chainlink's CCIP directory (https://docs.chain.link/ccip/directory ; not fetched, [U]). Use as a label allow-list, not as the primary signal.

### 1d. Other owners
- Zero address and dead addresses (`0x0000...0000`, `0x0000...dEaD`): "renounced/no owner" => no key can change settings, but also nobody can fix them; verdict "renounced", not "single key". Note `Ownable2Step` here rejects zero owner in the constructor (`OwnerCannotBeZero`), so owner == 0 on a pool means something is off => unclassifiable.
- Governor / Aragon / Zodiac / DAO modules: no standard single read. Recognise Governor by `timelock()`/`proposalThreshold()` [U]; otherwise "not readable". Do not guess.
- Proxy admin vs owner: EIP-1967 admin slot `0xb53127684a568b3173ae13b9f8a6016e243e63b6e8ee1178d6a717850b5d6103` and implementation slot `0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc` (computed: keccak256("eip1967.proxy.admin"|"...implementation")-1; verify with a test). If the pool is a proxy, its ProxyAdmin (usually a contract with `owner()`) can swap logic: classify that admin too. Slot read via `eth_getStorageAt`; not every free node serves it [U]. Beacon proxies: slot differs, treat as unknown.
- Pending owner / pending admin: not reachable by view for CCIP pools (see 0); for TokenAdminRegistry, `pendingAdministrator` is in `getTokenConfig` [P]. Report pending separately; never let pending change the verdict to clear.
- Contract that is an EOA-owned "ownerless router" or a minimal forwarder: unknown.

### 1e. How other trackers state confidence
- L2BEAT permissions spec [P https://docs.l2beat.com/l2b_specs/permissions.html]: list the ultimate permissioned actors (EOAs, multisigs, governors); a multisig shows threshold, size, modules; a non-EOA actor needs a description of its own code; nested multisigs controlled by one entity are folded. Project pages render "Multisig X/Y" and generic "EOA 1" labels; unverified source gets an explicit warning; role chains render as "admin: ProxyAdmin; ultimately <actor>" [search summaries of l2beat.com pages; U on exact wording]. The spec says nothing about confidence scores or unknown contracts [P: absent] - there is no published rule to copy; what they do is surface "unverified" visibly rather than guess.
- L2BEAT stages: Security Council needs >= 8 members and threshold > 75%; otherwise it is a "simple multisig" (https://medium.com/l2beat/stages-update-security-council-requirements-4c79cea8ef52 via search summary [U-ish]). Useful as an external yardstick, but ccip.dev should avoid grading quality, only flag 1-signer.
- DeFiLlama / DeFiScan / Exponential / Blockaid admin-risk rules: NOT confirmed (searches returned nothing primary). Do not cite them.

## 2. Reading many values cheaply

### 2a. Multicall3  [P https://raw.githubusercontent.com/mds1/multicall/main/README.md]
- Address `0xcA11bde05977b3631167028862bE2a173976CA11` on 100+ chains (README says both "100" and "250"). A few unofficial deployments exist at other addresses; the Ancient8 instance is the one known-bad deployment (custom contract at that address): never trust the address blindly on a chain you haven't probed.
- `aggregate3((address target,bool allowFailure,bytes callData)[]) returns ((bool success,bytes returnData)[])` selector 0x82ad56cb. `tryAggregate(bool requireSuccess,(address target,bytes callData)[]) returns ((bool,bytes)[])` selector 0xbce38bd7. Helpers: `getChainId()` 0x3408e470, `getBlockNumber()` 0x42cbb15c, `getEthBalance(address)` 0x4d2301cc.
- ABI return for aggregate3: head word 0x20, array length n, then n offsets (relative to array-content start) to each `(bool success, bytes returnData)` tuple; each tuple: word0 success, word1 offset to bytes (0x40), then length + padded data. Always use allowFailure=true so one reverting target (EOA, missing function) does not kill the batch; then treat success=false or empty returnData as "no answer", never as a value.
- Validate per chain once per run: `eth_getCode(multicall3)` non-empty AND `getChainId()` equals the expected chain id (guards against Ancient8-style squatters and mis-keyed chains). Cache the verdict in D1.
- Gas cap: `eth_call` is capped by node `--rpc.gascap`; keep batches modest (e.g. 50-100 sub-calls per aggregate3 for ~4 view calls per address). Exact public caps unconfirmed [U].
- Deployless multicall (no contract on chain) [P-ish: viem docs via search; https://viem.sh/docs/contract/multicall]: send `eth_call` with NO `to`, `data = multicallCreationBytecode ++ abi.encode(constructor args)`, where the constructor runs the calls and returns the result via `revert`/return data; decode like a normal return. Cost: about 6.6 KB of bytecode per request (many free endpoints cap request body size [U]). Fallback if deployless fails: individual `eth_call`s (3-4 per address). State-override variant (`eth_call` with `{"to": multicall3, ...}, "latest", {"<addr>": {"code": "<runtime>"}}`) works on geth-like nodes but many free providers reject overrides [U]. Recommendation: per-chain capability probe stored in D1: `multicall3 | deployless | single`.
- Pin the Multicall3 call itself to the pinned block: historical-block multicall needs the contract deployed at that block (viem doc note).

### 2b. JSON-RPC batching on free endpoints
- dRPC free plan: batch limit 3 items; over-limit returns HTTP 200 with an array where every call fails with "Batch of more than 3 requests..." (l2beat PR #13213); other reports say HTTP 500 [search summary]. 120,000 CU/min/IP normal, 210M CU / 30 days, floor 50,400 CU/min under load [search summary of drpc.org/docs/howitworks/ratelimiting; page body not read: U]. https://github.com/l2beat/l2beat/pull/13213
- publicnode: 100 per batch; over-limit returns 200 + array with one "batch too large" error; Cloudflare gateway: 10 (returns a single error object, not an array); Alchemy advises <50; geth default 1000 (same PR).
- Ankr public (no key): batch max 10, about 1,800 req/min guaranteed, eth_getLogs max 1,000 block range. https://www.ankr.com/docs/rpc-service/service-plans/
- llamarpc: no limits found [U].
- Design rule: a batch response may be (a) an array in any order (match by `id`), (b) a single error object instead of an array, (c) an array of per-item errors that all say "batch". Implement the l2beat approach: on size rejection (HTTP 413, or whole-batch error mentioning "batch") halve the batch size down to 1 and remember per host for ~5 minutes; do NOT treat 401/403/429/5xx as size errors. Since Multicall3 already packs the reads into one eth_call, JSON-RPC batching is a minor gain; default to batch size 1 plus Multicall3, and use batches only for the few auxiliary calls (getCode/blockNumber) at <=3 items.
- "Retry elsewhere" errors: HTTP 429/5xx/timeouts, `-32005` limit exceeded, "rate limit"/"too many requests" text, "header not found"/"block not found"/"unknown block"/"missing trie node" (lagging or non-archive node). Permanent errors (don't retry on the same host): `-32601` method not found, `-32602` invalid params, `-32001/-32003/-32004/-32006` per the Zoltar triage (https://github.com/AugurProject/zoltar/issues/1359 via search summary). `execution reverted` from eth_call at the right block is a real answer (value = "no function"), not an RPC failure.
- With one endpoint per chain (project constraint) there is no failover: a failed chain means "not readable this run", carry forward the previous day's state with its age, never a fresh "clear".

### 2c. Pinning one block  [P https://eips.ethereum.org/EIPS/eip-1898]
- `eth_call` second param may be a hex block number or `{"blockNumber":"0x.."}` or `{"blockHash":"0x..","requireCanonical":true}`. Missing block => recommended error -32001 "Resource not found"; non-canonical with requireCanonical => -32000. Hash form is not supported by every free node [U]; prefer plain hex number.
- Recipe per chain: `eth_blockNumber` -> N; pick `B = N - confirmations` (e.g. 12 for L1-ish, 20-64 for fast L2s with reorg-prone sequencers [recommendation]); fetch `eth_getBlockByNumber(B,false)` once to record hash+timestamp; every read for that chain uses `B` and Multicall3 `getBlockNumber()` is NOT a check (it returns the call's block, useful to confirm the node actually executed at B). Slightly old blocks (a few to tens of blocks) are served by non-archive nodes from recent state (geth keeps 128 blocks of state, [U]); a lagging load-balanced backend answers "header not found" => retry with backoff 0.3-1.5s up to ~6 times then give up for this run (pattern from piplabs PR #64 and similar). Never use `latest` for the snapshot.

## 3. Cloudflare sizing (as of fetch today)
Workers limits https://developers.cloudflare.com/workers/platform/limits/ [P]:
- Subrequests per invocation: Free 50 external (+ 1,000 to Cloudflare services per the table); Paid 10,000 (configurable to 10M via `limits.subrequests` in wrangler). D1 and R2 calls count as subrequests; redirects count.
- CPU per Cron invocation: Free 10 ms; Paid default 30 s (up to 5 min) when the interval is under 1 hour, up to 15 min when the interval is 1 hour or more (a daily cron qualifies). Wall time per Cron invocation 15 min. Simultaneous open outbound connections 6 per invocation: fetches beyond 6 queue, so concurrency of ~6 is the real cap on fan-out.
- Cron Triggers: 5 per account Free, 1,000 Paid (the doc lists it per account, not per Worker). Trigger changes take up to 15 min to propagate and runs missed meanwhile are skipped. UTC. https://developers.cloudflare.com/workers/configuration/cron-triggers/
- Free daily requests 100,000.
- On Free, 1,240 entries across ~80 chains cannot finish in one invocation (50 external subrequests). With Multicall3 you need roughly (chains x (1 code/probe + ~2-3 multicalls)) ~ 200-400 fetches plus D1 writes: fits Paid in one run, not Free. Spread on Free: cursor per run, ~10-12 chains per invocation, over multiple cron ticks, or use Workflows/Queues.
D1 [P https://developers.cloudflare.com/d1/platform/limits/ and /pricing/]:
- Queries per invocation: Free 50, Paid 1,000; a `db.batch()` counts as one query. 100 bound parameters per statement; max SQL statement 100 KB; row/blob 2 MB; query timeout 30 s; DB size Free 500 MB, Paid 10 GB; account storage 5 GB Free / 1 TB Paid. Batch statement cap not documented there.
- Free rows read 5M/day, written 100k/day (reset 00:00 UTC). Paid includes 25B reads/month and 50M writes/month. 1,240 entries x (a few rows each) is far under writes; the read risk is full scans, so index the lookup columns (matches the repo memory on D1 read spikes). Only write changed rows: compare the new snapshot hash to the stored one and skip identical rows.
R2 [P https://developers.cloudflare.com/r2/platform/limits/]: 1 write/second per object key (429 above); 5 TiB object max; per-bucket management ops 50/s. A per-token JSON page at 1,240 keys, written sequentially or at modest concurrency, is fine; never rewrite one hot key quickly.
Long jobs [P]:
- Workflows (https://developers.cloudflare.com/workflows/reference/limits/): available on Free; Free: 10 ms CPU/step, 1,024 steps, 50 subrequests per instance(request), 100 concurrent instances; Paid: 30 s CPU/step (to 5 min), 10,000 steps (to 25,000), 10,000 subrequests (to 10M). Each step gets its own limits, which is the usual way to get "one chain = one step" with automatic retry; `step.sleep` doesn't count toward steps.
- Queues (https://developers.cloudflare.com/queues/platform/limits/): usable on Free per that page; message 128 KB, consumer batch max 100, 15 min wall, 100 retries, retention fixed 24 h on Free. Free daily operations quota not stated there [U]; check pricing before relying on it.
- Simplest fit for this repo (matches the existing cron style): one D1 `job_cursor` row, each run processes the next K chains and updates the cursor; or fan out one Queue message per chain from the daily cron (each consumer invocation has its own 1,000/10,000 subrequest allowance on Paid). No paid data is OK; note Workers Paid is a CF plan, not a data source, but the repo memory says free tiers only: so design for Free (50 subrequests, 10 ms CPU, per-chain ~4 subrequests) as the binding constraint. 10 ms CPU on Free is tight for hand-rolled hex decoding of 1,240 entries; measure. ## 4. Telegram Bot API [P]
- Single chat: avoid more than 1 message/second; bursts allowed, then 429. Group: 20 messages/min. Bulk broadcast to many chats ~30/s. https://core.telegram.org/bots/faq
- 429 body includes `parameters.retry_after` (integer seconds): "In case of exceeding flood control, the number of seconds left to wait before the request can be repeated" (ResponseParameters, https://core.telegram.org/bots/api). Sleep `retry_after`+1 s then retry once; if retry_after exceeds the Worker's remaining budget, persist the unsent post in D1 and stop.
- Caption on sendPhoto: 0-1024 characters after entities parsing; sendMessage text 1-4096 characters (same doc). Existing repo behaviour: escape "<" in HTML captions (git log f4df678). Count length after parsing, not raw HTML bytes.
- For channels, the "20/min" figure is documented for groups; channel behaviour is not separately documented [U]: keep <= 1 msg/s and <= 20/min per channel.

## 5. Pitfalls and conservative publication rules (mostly synthesis; sources inline)
- Load-balanced endpoints answer from nodes at different heights: "header not found"/null for block N is a lag symptom, not data; retry with backoff, do not record as result (sources: MetaMask issue 7234, piplabs PR 64, Zoltar #1309/#1359 via search; treat as community evidence).
- Rules to implement:
  1. Two-snapshot confirmation: a flag may be PUBLISHED only if the same verdict is computed from two independent reads (different pinned blocks, e.g. B and B-N, from different runs or >= 1 h apart). Single-run verdicts stay "pending" and are not posted. With one endpoint per chain this guards against stale/partial answers, not against a malicious endpoint.
  2. Asymmetric states: unknown, error, decode failure, partial resolution, depth cap hit, any unreadable principal => "not readable". "Clear" requires a positively identified structure with proof (e.g. Safe pinned singleton + threshold >= 2 and >= 2 distinct nonzero owners, or timelock whose proposers/bypassers were fully resolved). Absence of evidence is never "clear".
  3. Change detection: posting an alert for a change (new owner, threshold drop) requires the new value to hold on the confirmation read; compare owner addresses case-insensitively (checksum vs lowercase), strip `0x000...` padding when decoding address words, and verify the high 12 bytes are zero.
  4. Decode strictly: check returndata length >= expected, offsets within bounds, array length sane (cap e.g. owners <= 200), bool word is 0 or 1. A malicious or quirky contract can return garbage to `getOwners()`.
  5. Upgradeable/proxied owners: a Safe or timelock behind a proxy can change its own rules; record the implementation/singleton address in each snapshot and treat a change as an event.
  6. Contract identity can be spoofed by selector coincidence; require corroborating probes and known-codehash lists (section 1c).
  7. Record provenance per verdict: chain, block number+hash, endpoint host, probes returned, timestamp; show "as of block B" and age on the page. L2BEAT's practice of showing explicit "unverified" warnings and ultimate actor chains (not just the direct owner) is the closest published model.
  8. Never classify from `eth_getCode` alone for "multisig": only a successful Safe/MCMS decode counts.
  9. Don't alert on the first observation of a new entry (no baseline), only publish the page with the current state.
  10. EIP-7702 means "EOA" is no longer a permanent property: re-check code each run; a delegated or newly delegated owner is itself an event.
